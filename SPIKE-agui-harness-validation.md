### Q4 — AG-UI route registration mechanism

**Answered.** The `ChatApi` construct (generated by `ts#api --framework=trpc --infra=rest-lambda`)
exposes its underlying `aws-cdk-lib/aws-apigateway.RestApi` as a public `api` member
(`packages/common/constructs/src/app/apis/chat-api.ts` extends `RestApi<Operations,
TIntegrations>`, `core/api/rest-api.ts:81` — `public readonly api: _RestApi`). That means the
`/agui` route needs **no change to the generated construct at all**:

```ts
const aguiResource = chatApi.api.root.addResource('agui');
aguiResource.addMethod(
  'POST',
  new LambdaIntegration(aguiHandler, { responseTransferMode: ResponseTransferMode.STREAM }),
  { authorizationType: AuthorizationType.IAM },
);
```

This was written directly in the CDK application stack (`spikes/agui-harness-validation/infra/application-stack.ts`)
and `cdk synth` succeeds. Two behaviours confirmed by reading (not yet deploying) the generated
construct source, worth calling out for the generator design:

- **CORS preflight is automatic.** `ChatApi` attaches `Aspects.of(this).add(new
  AddCorsPreflightAspect(...))` on its own scope (`chat-api.ts:139`). CDK Aspects visit the whole
  construct tree at synth time, so a resource added as a descendant *after* the `ChatApi`
  constructor runs — as `chatApi.api.root.addResource('agui')` is — still gets an OPTIONS method
  added. No extra wiring needed for CORS.
- **The IAM authorizer is inherited by default**, since `ChatApi` sets
  `defaultMethodOptions: { authorizationType: AuthorizationType.IAM }` on the underlying
  `RestApi`, and `resource.addMethod()` falls back to the API's default method options when none
  are passed explicitly. The spike still passes it explicitly for clarity/documentation value.

**Consequence for the generator (Epic #13):** the recommendation in §12 Q4 — "prefer a
connection-generator patch that attaches the extra route + integration" — is confirmed as the
right shape, and it turns out to need **no GritQL patch to the `ChatApi` construct's own source**.
The connection generator's `harness-trpc-config.ts` can add the resource/method/Lambda from a
*separate* file (e.g. patching `application-stack.ts` via GritQL to insert the
`chatApi.api.root.addResource('agui')...` block, guarded the usual `not contains` way) without
touching the `ts#api` generator's templates. This is simpler than the design doc anticipated — no
"documented construct hook" fallback needed.

One thing this doesn't yet confirm: whether the raised Lambda timeout for the `/agui` handler
needs any special interaction with the API's other (30s-timeout) operation handlers, since it's a
wholly separate `NodejsFunction`/`LambdaIntegration`, not a patch to the shared
`defaultIntegrationOptions`. Because it's a separate function, it can simply be given its own
`Duration.seconds(...)` without touching the tRPC operations' 30s default at all — arguably
cleaner than patching the shared default.

### Q5 — Tool-call stream shape

**Answered from the AWS SDK's TypeScript types** (`@aws-sdk/client-bedrock-agentcore@3.1111.0`),
pending empirical confirmation once a Harness with `allowedTools` is actually invoked with a
tool-triggering prompt:

`InvokeHarnessStreamOutput` is a Converse-shaped discriminated union — `messageStart`,
`contentBlockStart`, `contentBlockDelta`, `contentBlockStop`, `messageStop`, `metadata`, plus error
variants. Tool calls are represented exactly like Bedrock Converse tool-use streaming:

- `contentBlockStart.start.toolUse` → `{ toolUseId, name }` — start of a tool call.
- `contentBlockDelta.delta.toolUse` → `{ input: string }` — a partial-JSON chunk of the tool's
  input arguments, keyed by `contentBlockIndex`.
- `contentBlockStop` → end of that content block (text or tool-use).

This maps cleanly onto AG-UI's tool-call events, 1:1 with no impedance mismatch:

| Harness stream event | AG-UI event |
|---|---|
| `contentBlockStart.start.toolUse` | `TOOL_CALL_START { toolCallId: toolUseId, toolCallName: name }` |
| `contentBlockDelta.delta.toolUse` | `TOOL_CALL_ARGS { toolCallId, delta: input }` |
| `contentBlockStop` (for a tool-use block) | `TOOL_CALL_END { toolCallId }` |

The mapper in `spikes/agui-harness-validation/chat-api-agui/converse-to-agui.ts` implements this
(tracking `contentBlockIndex → toolCallId` since the delta/stop events don't repeat the tool's
name or id) and has unit tests exercising a synthetic tool-call sequence
(`converse-to-agui.spec.ts`) — they pass without a deployed Harness, since the mapper is pure.
**Recommendation for the generator confirmed:** this is a small additive change once `allowedTools`
support lands, not a wire-contract break — the design doc's §12 Q5 recommendation stands, but the
mapper can be built now that the shape is confirmed.
